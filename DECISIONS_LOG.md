## O5 — assessment scoring + path fit (ROADMAP §2)
- What: (a) `src/core/assessment.ts` reads interest, skill and strength answers from records and returns a 0–100 level per dimension (mean of the given 1–5 ratings / 5) and a count of dimensions with data. (b) `pathFit()` in the same file matches the user's items to `PATHS` in `src/library/paths.ts` by theme and returns up to 3 matches with a plain reason for each. (c) `src/ui/assessment.ts` renders both as simple cards at the top of the Plan screen.
- Why: Spec §3.1 (Discover) and §3.3 (Path fit) need an assessment that works without AI and shows why each path was suggested.
- Rules chosen: unknown ≠ 0. A missing rating stays null ("No rating given yet"); a dimension with no items is "Not enough data yet"; a user with no answers gets no paths, not a guess. Weights are fixed and visible in code: skill 3, interest 2, strength 1, one weight per theme (strongest source wins). Items no keyword can place are listed as "could not place yet", not dropped. Ties keep library order, and record order is by id, so the output is stable. No rank, grade or percentage of the person is shown; the 0–100 level is internal and the card shows the average out of 5.
- Path library: 10 generic, neutral paths drafted by the builder. Each has what it needs, a first small test and, where relevant, a check before starting (privacy of client records, local food-sale rules, interest-based credit). No income, return or success figures. Marked as a draft that has not been reviewed (যাচাই হয়নি). Halal filter (Spec MR-31) is partly covered by the "avoid interest-based deals" caution only; a full filter needs a qualified reviewer (Owner, D-D/MR-31).
- Matching: theme keywords in Bangla and English (English matches at word start). Matching is keyword-based, so it is rough; it can miss or mis-tag a phrase. The fix is to add keywords in `THEME_KEYWORDS`, not to add AI.
- Bangla: new strings are a draft pending native review (TM-TST-161).
- Alternatives: a numeric fit percentage (rejected: looks like a prediction and invites ranking); AI matching (rejected: D-C); keeping matches on a separate Journey page (rejected for now: Plan already has the answers and the cards are short).
- How to undo: remove `assessmentSection(cp.recs, lang),` from planScreen in `src/ui/screens.ts`; delete `src/ui/assessment.ts`, `src/core/assessment.ts`, `src/library/paths.ts`, `tests/o5_assessment_fit.test.ts`; delete the `assess.*` and `fit.*` keys in `src/i18n/packs.ts`.

An event that does not happen that day is `null`, never 00:00. Phone notification only when permission is already granted (permission is asked when the owner switches an alert ON, via the tap). Otherwise an in-app card at the top of every screen. Lock-screen text goes through the O8 rule (`buildNotification`, privacy "worship"): neutral unless "show details" is on for worship.

The method angles and Asr factor are a standard choice, not verified against the official table. Official Bangladesh timetables may use different angles or Asr convention; if so, change the named constants in `src/core/prayer.ts` (one place) and update `REF` in the test with the same change in `tools/prayer_reference.py`.
- Why: owner asked for on-device prayer times with a standard formula, no network, no licensed timetable, and a one-tap log that keeps no score.

## 2026-11-07 — At-rest encryption of real records built (option C, stage 1)
- What: real records can be sealed on this phone. Key format: a random 256-bit data key, wrapped with AES-GCM-256 under PBKDF2-SHA256 (600 000 rounds, reusing `cryptoBackup.ts`) of a passphrase (8+ characters, digits only refused). The wrapper is stored under `tm:secret:vault` (state `migrating`, `on` or `disabling`, a progress marker, a wrong-try counter). Only `values` and `links` of REAL records are sealed (AES-GCM, new random 12-byte IV on every write, `real|<id>` as AAD, marker `enc: 1`); ns, id, entity, schemaVersion, createdAt and ownerId stay plain, so the IndexedDB indexes still work. Demo records are never sealed. The key is held in memory only; the app asks for the passphrase at every start (unlock screen), so the PIN lock stays a screen lock.
- Write path: `mirrorToRepo` is the only place that seals, only for real records while the vault is on. No key (locked, or a tab that missed a change in another tab) or a crypto failure goes to the save banner and the plain value stays in memory, never written plain. A sealed record that cannot be opened is shown empty ("Can't open" count in the card) and its ciphertext is never overwritten or deleted.
- Turning on (every step must pass, otherwise nothing is changed): plain-words warning plus tick; recovery file (encrypted backup with a SEPARATE passphrase, opened again as a test before it is offered); second tick; a safety copy sealed with the new key and opened again as a test; then in-place migration, batch size 200, each batch written and read back before the next, progress marker in the vault settings, state flips to `on` only when no plain real record is left. Interrupted runs are resumable and stay fully readable (mixed state). Snapshots: the snapshot store seals the real part with the data key (or drops it when no key); older plain snapshots are sealed at activation. Plain exports (CSV, snapshot file, one-tap backup) stay explicit user actions and now show a "not encrypted" note.
- Turning off: needs the passphrase (with the same wrong-try slowdown as the PIN lock); opens records in place in batches (mixed state stays readable if it fails), reopens sealed snapshot parts, then removes the settings. Forgot passphrase: the unlock screen restores the real records from the recovery file (replaces the locked copy, typed tick) and turns the vault off. Forgot PIN never touches the vault.
- Two tabs: Web Locks (`tm-vault-run`) so only one tab migrates; a stale tab cannot write plain over sealed data (the active check reads the settings on every write, and the key counts only while the stored wrapper is the one it was opened from).
- Measured: 10 000 records seal in about 1.6 s and open in about 0.65 s with node WebCrypto and a plain Map (tests/data_vault.test.ts). In real headless Chromium IndexedDB (tools/e2e.mjs, VAULT-E2E-10K, shared sandbox CPU) the whole turn-on for 10 000 records took 15.2 s: two passphrase derivations, the sealed safety copy, sealing and read-back of every record. Fake IndexedDB is quadratic in records sharing an index value, so its number (1 000 records about 5 s) is a test-tool artefact. A real-phone timing is still an OWNER check (O1/O8).
- Alternatives: sealing `links` too was chosen over leaving parent ids plain; one shared password for backup and vault (rejected: a lost recovery file would then equal a lost key); sealing snapshots only when the key is held and dropping the real part otherwise (chosen) over keeping plain snapshots (rejected).
- Undo: Settings > Privacy > Encrypt real data > Turn off (opens everything in place); or restore the recovery file; or revert the commits of branch `worktree-agent-a5c474167f9775de4`. Schema version unchanged: the extra fields `enc`, `iv`, `ct` exist only on sealed real records, and the read path accepts plain and sealed records.
