## 1. Where B is better, and what I concede

1. **Restore is worse than I wrote.** I said restore "replaces records with the same ids". Code says otherwise: `restoreBackup` validates, then `await repo.clear(b.ns)`, then puts each record (`src/core/backup.ts` lines 38-39). A failure halfway leaves an empty namespace. B found this and designed the fix (preview, "Before restore" snapshot, automatic rollback, "go back" for 7 days). I concede fully and adopt it. This is the first PR to ship, before any layout work.
2. **Live "private by default" read-out.** I had static text. B's computed lines (consent, lock, lock-screen, connections, storage protection) are better and fit the charter rule "never claim what is not true". Adopted, placed at the top of Privacy and lock.
3. **Typed word for Clear real data.** I proposed a plain two-step. A typed word is a better guard against autopilot taps and has no timing that excludes slow readers. Conceded, with one change (see decision 5).
4. **Re-ask PIN for Delete and Restore when lock is on.** I missed the "someone holds the unlocked phone" case. Adopted.
5. **Extras I left out:** reduce-motion and high contrast, notification permission read-out, the translated `aria-label` bug in `langButtons()`, "Settings are not in backups", Mix missing from first-run (I noted it, B designed it), the daily demo-ask nag switch, `consentGate()` as a named single component, level B/A progressive disclosure. All adopted.
6. **Old routes.** B keeps `/more/data` and friends alive with a "moved" link. That breaks fewer existing tests than my redirects. I concede for the first release (see 2.6).
7. **Deen framing.** B's refusal to create a "Deen category" that feels like a piety dashboard is right. My "Prayer and alerts" already avoids it, but his reasoning goes into the decision log.

## 2. Where B is wrong, risky or unbuildable

1. **A 6th tab does not fit, and B knows it.** `nav` is `max-width:480px` and `.tab` is `flex:1; font-size:13px`. At 360 px, 6 tabs = 60 px each. "ট্র্যাকিং" style Bangla words at 13 px, and at 200 % text size, will wrap or clip ("Journey", "সেটিংস", "নামাজ" are all near 50 px). B says "decide by screenshot", which means the main plan may not survive its own test and the whole document (links, `More` split, crumbs) has to be rewritten. A proposal should pick the design that cannot fail. I keep 5 tabs by renaming the 5th.
2. **Two overlapping hubs.** B keeps `More` (content) and adds `Settings`, so `/more` and `/settings` both exist with a "Help and welcome" category in one and Topics/Glossary/Safety in the other. Safety and limits, Disclaimers and Capability status are "help" too. A person looking for Safety has two plausible doors. Test impact: the `more` tab tag stays and a second tab tag is added, so the tab-highlight tests double.
3. **The Settings home is too heavy, which undermines B's own principle 2.** Home = h1, 3 inline controls, 2 status cards, 8 categories, a danger link, search. At 100 % that is about 3 screens. At 200 % text it is a long scroll, and B hides search at 150 % and 200 %. That is backwards: low-vision users, who scroll the most, lose the quick-find. Hiding it "because it is advanced" is wrong; a search box is a lower cognitive cost than 8 cards. My home keeps the box always visible and uses a one-line status strip instead of two cards.
4. **Inline home controls make a hole in the category list.** Language, Theme, Text size live on the home, but the category is named "Language and look" and holds only Design version and the reduce-motion pair. A person who taps "Language and look" for language finds it missing. Either all of Look is on the home (too big) or none (my choice, plus the status strip showing current language and a one-tap globe).
5. **Backup reminder filed under "Reminders and prayer".** Row 32 is a backup safety control; B puts it with prayer alerts to make a "reminders" category. A user fixing backup problems will not look under prayer. Also it makes the Backup page split in two. The Today card already links to Backup, so Backup is where it must live. A "Reminders" category is a nice word, but it is grouped by mechanism (notifications), not by task.
6. **"Old routes keep working and show a one-line moved link" leaves dead pages.** `/more/data`, `/more/connections` and `/more/rules` would render a stub, not the settings. Bookmarks, the DEMO banner, tests and the service worker precache list point at them. Every stub is another screen to test in 3 languages and another place for the user to take an extra tap. A redirect (`location.replace`) is one table and no screen. I still concede that for the first release a stub is lower risk for existing tests, so: redirect in the app, and update the old route tests in the same PR to assert the redirect.
7. **Master Detail level is ambiguous.** B says the master "sets all" and, later, "Same as master is stored as absence of a key". Those are two different behaviours. "Sets all" would erase the person's exceptions. B's engineering note does not say how the reader tells "never set" from "set to full". `viewBar` today defaults to `full`; the reader needs a change. B understated this (it is the main code change in that PR).
8. **Withdraw consent as "read-only" is big, not small.** B's semantics (no new real writes, no real export, existing real entries shown read-only) touch every real write path: `entry.ts`, capture, habits, diary, import, snapshots, CSV, prayer place. B correctly marks it as an owner-level D-B question, but still lists it in the build order inside PR 4 as if it were a component swap. Safer first version: withdraw only stops new real writes and shows the count; "hide" or "read-only" waits for the owner.
9. **Start real as a full page.** Replacing the inline confirm card with a page is fine, but B routes the DEMO banner to `#/settings/data-mode/start-real`, a 3-level route. Along with `/backup/restore` and per-facility connection pages, that is route-regex growth in `ROUTES` plus one lazy chunk each. Not unbuildable, but 12+ new routes where 9 would do. I would use anchors and `?hl=` instead of pages for small things (Start real, Place).
10. **Typed word in Bangla.** B says BN "ডিলিট", EN "DELETE". On a Bangla phone keyboard the same word can be typed with different conjunct or vowel forms; and in Mix mode which word? Without a normalisation rule the guard can lock out the right user. Accept either word in any language, case-insensitive, trimmed.
11. **Pre-restore snapshot holds real data for 7 days** and is exempt from "keep N". That is a new copy of real data. It must be covered by `scrubRealParts` on Clear real, and by app lock. B mentions scrub for clear-real but not that this exemption must be tested.
12. **Search as an afterthought.** B has no registry and no test that each setting has one home. His "one home per key" test is mentioned in the PR tests but nothing keeps it true later. My registry gives both quick-find and the test.
13. **Level A/B fold per sub-screen** adds a stored fold state per page (localStorage) and a "6 more options" counter that must be kept correct in 3 languages. Reasonable, but it hides connections, rules and CSV behind a tap on pages whose only purpose is those things. I would fold only inside long pages (Prayer, Backup), not on Connections or Plan.

## 4. What both of us missed

1. **Settings are not in any backup** (B noted it, neither fixed it). After restore or a browser clear the phone looks reset. Decide: include non-sensitive look/layout prefs in the backup file (versioned, no secrets, no consent, no PIN, no keys) or say it plainly on the Backup page. Recommend saying it plainly now and adding it later with a schema version.
2. **Service worker precache and offline.** New routes and lazy chunks must be in the precache list; a Settings page that 404s offline breaks "offline after first visit". Test offline on every `/settings/*` route.
3. **i18n key parity.** Every new label needs en, bn and mix; there should be a test that fails if a key is missing from a pack. Both proposals only say "Mix column".
4. **Focus and screen-reader announcement on hash-route change.** Both talk about heading order; neither says that route changes should move focus to the new h1 and announce the title. This matters for all of `/settings/*`.
5. **Two open tabs / storage events.** A language or consent change in one tab leaves the other stale; the lock and consent state should re-read on `storage` events, at least for consent and lock.
6. **Locked state and deep links.** I covered `isLocked()` first in `render()`; B covered re-ask PIN. Neither tested that a `?hl=` or deep link to `/settings/danger` while locked ends on the lock screen and, after unlock, returns to the same route.
7. **Back-button behaviour after a language switch or a destructive result** (B has the replay case; neither handles `location.replace` and history entries together).
8. **Registry must also list the values that are computed defaults** (backup reminder is "on only after real data and tick"; the user cannot see why). Show the effective value and the reason in the row.
9. **The Stuck flow and Plan mode.** Both let `/stuck` write plan mode and say so; neither says how the user returns from Pause. Needs a visible "Pause is on, end pause" chip on Today.
10. **D-D and D-C wording** on Connections: both leave it as is; the page should state the one-line truth "No connection sends anything yet" only from a computed check (no network code is active), not static text.
11. **Evidence plan.** Neither lists which TM-REQ/TM-TST rows this work can verify, or requires a Register update from real test artifacts, as the charter does.
12. **Owner decisions to log, not ask:** tab rename, additive key, restore confirm and consent-withdraw semantics (the last needs one short owner question with the recommended default "stop new real writes only").
