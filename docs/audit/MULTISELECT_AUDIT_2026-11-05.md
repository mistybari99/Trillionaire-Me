# Selection audit — 5 November 2026

The owner asked to find places where several selections make sense but only one is accepted. This source audit examined the catalog choice/list definitions and the actual selectors in the UI. It changes selection controls while preserving the existing data model, planner, progress and financial rules.

| Area | Observed contract and decision |
| --- | --- |
| Task creation and task editing: linked goals/sub-goals/projects | **Fixed.** Top-level goals already allowed several links, but the single “Which part?” select replaced every saved ID in that branch with one ID. Grouped native checkboxes now select each actual goal ID independently, preserve sibling selections and allow separate parent/child selection without cascading. |
| Habit creation and habit goal editing | **Fixed through the same picker.** Both consumers now preserve multiple sibling goal parts. Habit links remain contextual and do not enter progress percentages. |
| Goal-link limit and old records | The existing global five-ID limit counts roots, child parts and retained hidden/dangling IDs together. A sixth choice is reverted with a polite status message and keeps keyboard focus. Retired linked goals remain available for removal. Hidden IDs are not silently removed. Existing list storage, Unknown-on-clear and the task's legacy first-link mirror remain unchanged. |
| Habit weekdays | **Already multiple in the reachable habit form.** Weekday toggles select several days. The catalog declares `habit.days` as `multichoice`; the generic intake renderer incorrectly treated any option-backed field as a scalar dropdown. The renderer now supports real checkbox groups and string-list roundtrips, including the legacy comma-separated weekday representation. This is a latent renderer contract fix: `habit.days` is step 0 and currently uses its dedicated habit form, not progressive intake. |
| SWOT lists and task/habit goal lists | Dedicated screens already support multiple entries. Generic catalog rendering previously flattened list values into a text input/scalar; it now uses one-entry-per-line textareas and saves arrays. Existing list entries reopen separately; clearing an existing list stores Unknown. No current intake field of this type is newly enabled by this work. |
| Skills, interests, strengths, values and resources | These are repeatable records with individual evidence/levels, not a fixed choice list. Multiple records are already representable; converting each record's level/kind to a selection array would change its meaning. No blanket conversion. |
| Learning preference (`approach.learning_style`) | Several preferences are plausible, but the current catalog and `approachFrom` reader explicitly store one scalar answer. Kept unchanged in this repair; changing it needs a deliberate field/reader migration instead of accepting arrays that the existing reader would hide. |
| Goal area, horizon, kind, status, progress mode and weighting | Kept scalar. These select a primary grouping, placement, lifecycle state or calculation rule. Multi-valued states would require separate business semantics, especially privacy and grouping for Deen areas. |
| Task priority, size, prerequisite, responsible role; goal parent | Kept scalar: a task has one priority/size and the current scheduler expects one predecessor; the hierarchy has one structural parent. Choosing several would alter scheduling or hierarchy logic. Goal links already provide the appropriate multiple contextual association. |
| Venture stage, resource/source/constraint kind; team holder/handover status | Kept scalar per record. More ventures/resources/sources/constraints/roles can be separate records; one stage or status cannot simultaneously be its opposite. No existing multi-valued sales-channel field was found. |
| Finance kind/scope/period and venture attribution | Kept scalar. Each line has one accounting type/unit/period and one attribution; selecting several would risk duplicate totals. Separate lines represent separate amounts. |
| Prayer plan type, repeat, selected prayer and status; health entry kind | Kept scalar per plan/entry: one dated health measurement has one unit; one prayer-linked reminder resolves one prayer time. Several entries/plans represent distinct measurements or reminders without changing calculations. |
| KPI and stage-exit measure/period; reality-event state/action; reminder target/state | Kept scalar because these choose one calculation, transition or target. |
| Language/theme/design/data namespace, unknown state, detailed/compact, date/filter controls and import column mapping | Kept exclusive. These are settings or one-to-one mappings rather than content tags. |

Implementation: `src/ui/goalLinks.ts`, `src/ui/fieldInput.ts`, and the input renderer import in `src/ui/screens.ts`. No catalog field, schema version, migration, stored calculation or original Register file changed. The generic renderer keeps unsupported already-saved multichoice codes visible/selected rather than dropping them silently.

Regression evidence is in `tests/goal_picker.test.ts`, `tests/habit_goals.test.ts`, `tests/goal_tree.test.ts`, `tests/enc_backup_ui.test.ts` and `tests/field_input.test.ts`: sibling save/reopen/remove; parent removal without clearing children; five-ID limit including hidden IDs; retired links; no default selection; task/habit roundtrip; typed generic lists/multichoice and scalar behavior. Browser geometry, keyboard and deployment verification are recorded separately by the integrating agent.
